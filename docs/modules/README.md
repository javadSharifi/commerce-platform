## وضعیت قراردادها

- جدول‌های نام‌برده از بریف و چک‌لیست آمده‌اند. انواع ستون، روابط دقیق، ایندکس‌ها و سیاست‌های RLS در P0.2 و `docs/database.md` تدوین می‌شوند. قیدهای lookup و Worker در D-24 و D-28 ثبت شده‌اند.
- عملیات API با نام کاربردی آمده‌اند. مسیرها، schema درخواست و پاسخ، کدهای وضعیت و قرارداد دسترسی با OpenAPI مصوب در `packages/contracts/openapi.yaml` تعیین می‌شوند. پیشوند `/v1` و تفکیک Public و Admin در تسک‌های `P0.3.1` و `P0.3.2` دنبال می‌شوند.
- نام هر فایل برای پیدا کردن مشخصات یک حوزه است. ساختار پکیج‌های Go و مرزهای استقرار را با معماری ثبت‌شده تطبیق بده.
- جزئیات اجرایی در حدود D-30 در قرارداد مربوط ثبت و آزموده می‌شوند. برای تصمیم خارج از آن اختیار با صاحب پروژه هماهنگ کن. [تصمیم‌های معماری](../DECISIONS.md)

## قواعد مشترک پیاده‌سازی

- محدودهٔ Tenant از Host تأییدشده یا عضویت احرازشده می‌آید. برای داده‌های tenant-scoped از تراکنش با context فروشگاه، query پارامتری sqlc و RLS استفاده کن. [الگوی ماژول](../patterns/01-tenant-scoped-module.md) · [الگوی Migration و RLS](../patterns/02-migration-rls.md)
- ماژول‌ها از مرز سرویس یا interface با هم کار می‌کنند. اجرای کار اتمیک مثل ثبت سفارش و کسر موجودی باید در همان تراکنش باقی بماند. [ضدالگوی AP-17](../ANTI_PATTERNS.md)
- برای هر منبع tenant-scoped سناریوی خواندن و نوشتن دو فروشگاه را با PostgreSQL و نقش runtime پوشش بده. [الگوی تست ایزولاسیون](../patterns/03-tenant-isolation-test.md)
