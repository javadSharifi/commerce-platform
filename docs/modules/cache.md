# Cache — کش عمومی، Outbox و Worker

> قبل از کار روی هدر کش، رویداد تغییر داده، Worker یا ابطال کش این فایل را بخوان.

**تسک‌ها** — `P3.5`، `P5.1`، `P5.2`، `P5.4.4` و `P5.5.2`. [چک‌لیست پروژه](../../TASKS.md)

## مسئولیت و مرز

Storefront هدرهای کش صفحات را صادر می‌کند. ماژول‌های تغییر‌دهندهٔ داده رویداد Outbox را می‌نویسند. Worker URLهای متأثر را تعیین می‌کند و ماژول `cache` در Go آن‌ها را در CDN آروان purge می‌کند.

## داده‌ها و عملیات

| بخش | محدودهٔ ثبت‌شده |
| --- | --- |
| داده | `outbox_events` در PostgreSQL برای تغییر محصول، دسته، موجودی و تنظیمات مؤثر بر HTML عمومی |
| Storefront | `Cache-Control` برای صفحهٔ عمومی canonical مجاز و `no-store` برای پاسخ‌های شخصی |
| داخلی | خواندن Outbox با نقش Worker، تعیین URL محصول، دسته و در صورت اثرگذاری صفحهٔ اصلی، purge در آروان، retry و ثبت شکست نهایی |

## قواعد اجرایی

- کلید کش عمومی شامل Host و مسیر است. صفحات دارای query string از کش مشترک عبور می‌کنند. URLهای قدیم و جدید هنگام تغییر slug و صفحه‌های دسته یا خانه در صورت اثرپذیری در همان Tenant purge می‌شوند.
- سبد، حساب، checkout، نتیجهٔ پرداخت و دادهٔ شخصی `no-store` هستند. قیمت و موجودی نهایی خرید همواره از Backend بررسی می‌شوند.
- تغییر داده و ثبت رویداد در یک تراکنش‌اند. Worker پس از commit، ابطال را پیگیری می‌کند. پردازش موفق پس از نتیجهٔ معتبر ثبت می‌شود. ناموفق‌ها مسیر retry و dead-letter یا لاگ تعریف‌شده دارند.
- تغییر حالت خرید، شمارهٔ تماس عمومی یا «تماس برای قیمت» باید URLهای عمومی متأثر همان Tenant را تازه کند. Backend برای مجاز بودن خرید، حالت و قیمت جاری را از منبع اصلی می‌خواند.

## سناریوهای تست

- تغییر قیمت، پس از اجرای Worker، صفحهٔ محصول و دستهٔ متأثر را تازه می‌کند. کش B با تغییر محصول A ابطال نمی‌شود.
- rollback تغییر داده، رویداد قابل پردازش باقی نمی‌گذارد. شکست موقت CDN به retry می‌رود و شکست نهایی قابل مشاهده است.
- دو Host با مسیر یکسان کلید کش جدا دارند. صفحات شخصی و درخواست صفحه با query string وارد کش عمومی نمی‌شوند.
- پس از تغییر حالت خرید، شماره یا وضعیت قیمت A، صفحات مرتبط A تازه می‌شوند و صفحات B تحت تأثیر قرار نمی‌گیرند.
