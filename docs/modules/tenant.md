# Tenant — فروشگاه و محدودهٔ دسترسی

> قبل از کار روی ساخت فروشگاه، تشخیص Tenant یا تراکنش‌های فروشگاه این فایل را بخوان.

**تسک‌ها** — `P0.2.3`، `P0.3.3`، `P1.2.7`، `P1.3.1`، `P1.3.4` تا `P1.3.8` و `P1.4.2`. [چک‌لیست پروژه](../../TASKS.md)

## مسئولیت و مرز

Tenant نمایندهٔ یک فروشگاه است. ماژول، ایجاد و خواندن فروشگاه و انتشار محدودهٔ فروشگاه در context درخواست را پوشش می‌دهد. [Auth](auth.md) عضویت مدیر را بررسی می‌کند و [Domain](domain.md) دامنهٔ تأییدشده را به فروشگاه نگاشت می‌کند.

## داده‌ها و عملیات

| بخش | محدودهٔ ثبت‌شده |
| --- | --- |
| داده | `tenants`؛ `domains` و `memberships` برای تعیین محدوده با همکاری ماژول‌های مربوط |
| ثبت‌نام | ایجاد فروشگاه در جریان ساخت حساب مالک و عضویت `owner` |
| پنل | خواندن فروشگاه در محدودهٔ عضویت احرازشده |
| فروشگاه | انتقال Tenant حاصل از Host تأییدشده به context درخواست |

## قواعد اجرایی

- انتخاب فروشگاه در پنل ترجیح کاربر است. مجوز آن از عضویت معتبر همان کاربر به دست می‌آید. مقدار `tenant_id` در body، query یا header دلخواه اختیار دسترسی نمی‌دهد.
- برای دسترسی به داده‌های tenant-scoped، از `WithTenantTx`، query پارامتری sqlc با فیلتر Tenant و RLS استفاده کن. وضعیت Tenant در PostgreSQL به همان تراکنش محدود است.
- عملیات tenant-scoped بدون Tenant معتبر باید بسته بماند. جداول و lookupهای پیش از تشخیص Tenant طبق تصمیم مصوب خودشان بررسی می‌شوند.

## سناریوهای تست

- ساخت فروشگاه از مسیر ثبت‌نام، فروشگاه و عضویت مالک قابل استفاده ایجاد می‌کند.
- Host تأییدشده و عضویت معتبر، هر کدام Tenant درست را به مصرف‌کننده می‌دهند. در نبود محدودهٔ معتبر، عملیات tenant-scoped رد می‌شود.
- مدیر A داده‌های B را نمی‌خواند و تغییر نمی‌دهد. تغییر ورودی قابل‌کنترل درخواست نیز محدودهٔ مجاز را عوض نمی‌کند.
- درخواست‌های پشت‌سرهم برای A و B روی اتصال مشترک تنظیم Tenant را از تراکنش قبلی به ارث نمی‌برند. ایزولاسیون را روی PostgreSQL با نقش runtime بسنج.
