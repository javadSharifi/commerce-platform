# docs/DECISIONS.md — تصمیم‌های معماری و دلیلشان

> **هدف:** وقتی «راه ساده‌تر» به ذهنت رسید، این‌جا ببین آن راه قبلاً بررسی و **رد شده** است یا نه، و چرا.
> **قانون:** تصمیم‌های این فایل را **خودت عوض نکن.** اگر فکر می‌کنی تصمیمی اشتباه است، دلیلت را بنویس و از من بپرس (بخش «چطور تصمیم را عوض کنیم» در انتهای فایل).

تصمیم‌های `D-*` مربوط به فروشگاه‌سازند. قواعد محصول کارگاه، نوبت و دوره با شناسهٔ `PSY-D*` در [تصمیم‌های روان‌شناسی](psychology/DECISIONS.md) ثبت می‌شوند.

## D-01 — Modular Monolith، نه Microservices ✅

- **تصمیم:** یک Binary برای Go با ماژول‌های جدا (`auth`، `tenant`، `domain`، `catalog`، `inventory`، `order`، `payment`، `customer`، `shipping`، `theme`، `cache`).
- **چرا:** تعداد سرویس‌های همیشه‌روشن و مصرف RAM باید پایین باشد. تیم کوچک است. Microservices هزینه‌ی شبکه، دیپلوی و دیباگ را چند برابر می‌کند بدون اینکه در این مقیاس سودی بدهد.
- **وسوسه:** «این ماژول را جدا سرویس کنیم تا تمیزتر باشد» / «Kubernetes برای آینده.»
  **رد شد، چون:** پیچیدگی الان، برای نیازی که شاید هرگز نیاید.
- **حفظ امکان جداسازی:** مرز ماژول‌ها را تمیز نگه دار (ماژول‌ها فقط از طریق interface با هم حرف بزنند، `AP-17`)؛ هر ماژول sqlc و جدول‌های خودش را دارد.
- **بازبینی وقتی:** یک ماژول به‌طور واقعی به مقیاس یا استقرار مستقل نیاز پیدا کند (با عدد و اندازه‌گیری، نه حدس).

## D-02 — Multi-Tenancy: Shared DB + Shared Schema + `tenant_id` + RLS ✅

- **تصمیم:** همه‌ی فروشگاه‌ها در یک دیتابیس و یک schema؛ جداسازی با ستون `tenant_id` **و** Row Level Security.
- **چرا:** صدها/هزاران فروشگاه با یک زیرساخت. Migration یک‌بار اجرا می‌شود، نه هزار بار. مصرف منابع کمینه.
- **گزینه‌های ردشده:**
  - *دیتابیس جدا برای هر فروشگاه:* بهترین ایزولاسیون ولی Migration، Backup، connection و هزینه با تعداد فروشگاه‌ها منفجر می‌شود.
  - *Schema جدا برای هر فروشگاه:* تعداد زیاد schema مدیریت Migration و catalog دیتابیس را سنگین می‌کند.
- **وسوسه:** «RLS را بعداً اضافه می‌کنیم؛ فعلاً `WHERE tenant_id` کافی است.»
  **رد شد، چون:** یک Query فراموش‌شده = نشت داده بین فروشگاه‌ها. RLS شبکه‌ی ایمنی دوم است (`AP-04`، الگوی ۰۲). هزینه‌ی افزودنش بعداً خیلی بیشتر است.
- **بازبینی وقتی:** مشتری‌ای با نیاز قانونی/قراردادی به ایزولاسیون فیزیکی بیاید (می‌شود فقط برای او دیتابیس جدا داد).

## D-03 — Tenant فقط از دامنه یا عضویت ✅

- **تصمیم:** Storefront: tenant از Host **تأییدشده**. Admin: از عضویت احرازشده‌ی کاربر. هرگز از ورودی قابل‌کنترل کاربر.
- **چرا:** ورودی کاربر قابل جعل است؛ تغییر یک عدد نباید به داده‌ی فروشگاه دیگر برسد.
- **وسوسه:** «کلاینت `tenant_id` را در header بفرستد، ساده‌تر است.» ← رد (`AP-01`، `AP-12`).

## D-04 — Go + Chi + pgx + sqlc، بدون ORM ✅

- **تصمیم:** Chi برای HTTP، pgx برای دیتابیس، sqlc برای تولید کد Query، slog برای لاگ، golang-migrate برای Migration، validator برای اعتبارسنجی.
- **چرا:** کم‌مصرف، سریع، Binary واحد. sqlc کد را از SQL واقعی و type-safe تولید می‌کند، پس RLS، تراکنش و Queryها شفاف و قابل‌مرور می‌مانند.
- **وسوسه:** «از GORM/ORM استفاده کنیم تا سریع‌تر بنویسیم.»
  **رد شد، چون:** ORM تراکنش، `set_config` و RLS را مبهم می‌کند و Queryهای پنهان تولید می‌کند که نمی‌شود راحت بازبینی‌شان کرد (`AP-20`).
- **بازبینی وقتی:** sqlc برای یک نیاز مشخص ناکافی بود (مثلاً Queryهای فوق‌العاده پویا)؛ آن‌وقت یک ابزار کوچک‌تر، نه ORM کامل.

## D-05 — فقط PostgreSQL؛ Redis در نسخه‌ی اول نه ✅

- **تصمیم:** نسخه‌ی اول بدون Redis. کش HTML در CDN است، داده در PostgreSQL، و رویدادها در جدول Outbox.
- **چرا:** هر سرویس همیشه‌روشن RAM و پیچیدگی عملیاتی اضافه می‌کند. این معماری بدون Redis کار می‌کند.
- **وسوسه:** «برای session، rate limit یا کش، Redis بگذاریم.» ← فعلاً رد (`AP-20`).
- **بازبینی وقتی:** **اندازه‌گیری** نشان داد PostgreSQL یا CDN برای یک نیاز مشخص کافی نیست. آن‌وقت دلیل و اعداد را بنویس و از من بپرس.

## D-06 — Astro با SSR + کش CDN ✅

- **تصمیم** — Astro با `output: server` و Node adapter، HTML را رندر می‌کند. آروان فقط HTML عمومی مجاز را مطابق D-26 کش می‌کند. درخواست بعد از purge، HTML تازه دریافت می‌کند.
- **چرا:** SEO به HTML کامل نیاز دارد. Astro (در زمان نوشتن این سند) معادل داخلی ISR مثل Next.js ندارد؛ این مدل همان رفتار را با کش CDN می‌دهد بدون Build مجدد همه‌ی صفحات.
- **گزینه‌های ردشده:** Build استاتیک همه‌ی صفحات هر فروشگاه (با هزاران فروشگاه شدنی نیست)؛ SPA سمت کلاینت (SEO ضعیف).
- **تأیید محیط هدف** — در P3/P5 هدرهای origin، HIT و BYPASS و رفتار purge مسیرهای عمومی را روی آروان بررسی کن.
- **قید:** صفحات شخصی (سبد، حساب، checkout) هرگز کش عمومی نمی‌شوند (`AP-10`).

## D-07 — ابطال کش با Outbox و Worker ✅

- **تصمیم** — تغییر داده و ثبت رویداد Outbox در **یک تراکنش** انجام می‌شوند. Worker مقصدهای تأییدشده و URLهای متأثر را طبق D-26 به آروان می‌دهد و خطای موقت را retry می‌کند.
- **چرا:** رویداد هرگز گم نمی‌شود، حتی اگر Worker یا CDN موقتاً خراب باشد.
- **وسوسه:** «بعد از commit مستقیم CDN را purge کنیم، کوتاه‌تر است.» ← رد (`AP-11`): اگر همان لحظه پروسه بمیرد، کش کهنه می‌ماند و کسی نمی‌فهمد.
- **وسوسه ۲:** «فقط TTL کوتاه بگذاریم.» ← رد: یا قیمت کهنه می‌بیند یا کش بی‌اثر می‌شود.

## D-08 — یک Storefront با قالب‌های ماژولار، بدون کد دلخواه مشتری ✅

- **تصمیم:** یک پروژه‌ی Storefront؛ قالب‌ها (`minimal`، `classic`، `luxury`) پوشه‌های ماژولار با قرارداد مشخص (`ThemeConfig`) و `version`. مشتری فقط **تنظیمات** (رنگ، فونت، گردی گوشه) را عوض می‌کند.
- **چرا:** نگهداری یک پروژه به‌جای N پروژه؛ ایمنی (اجرای کد مشتری = خطر امنیتی و پایداری).
- **وسوسه:** «به مشتری اجازه بدهیم JS/Astro سفارشی بنویسد.» ← رد (`AP-14`).
- **قید:** قالب‌ها ورژن‌بندی می‌شوند تا به‌روزرسانی، فروشگاه‌های قبلی را خراب نکند.

## D-09 — یک پنل مدیریت مشترک ✅

- **تصمیم:** یک اپ Astro برای Admin که برای همه‌ی فروشگاه‌ها مشترک است. اگر کاربر عضو چند فروشگاه باشد، فروشگاه فعال را انتخاب می‌کند.
- **چرا:** یک پنل نگهداری می‌شود و تنظیمات هر فروشگاه داده است نه کد.
- **استقرار:** در نسخه‌ی اول، Admin و Storefront می‌توانند روی یک Astro Server اجرا شوند، ولی **از نظر کد و مسیر انتشار مستقل** نگه داشته شوند (`apps/admin` و `apps/storefront` جدا).

## D-10 — دامنه‌ی اختصاصی تأییدشده با SSL خودکار ✅

- **تصمیم:** هر فروشگاه دامنه‌ی خودش را ثبت می‌کند؛ سیستم رکورد DNS لازم را نشان می‌دهد، مالکیت را **تأیید** می‌کند، سپس دامنه را وصل و SSL صادر می‌کند. دامنه‌ی Apex با CNAME Flattening یا پروکسی پشتیبانی می‌شود.
- **چرا:** هر مشتری برند و دامنه‌ی خودش را می‌خواهد؛ فرایند باید بدون دخالت دستی باشد.
- **قید امنیتی:** دامنه‌ی تأییدنشده هرگز به Tenant وصل نمی‌شود، و endpoint «این دامنه مجاز است؟» برای Caddy فقط دامنه‌های تأییدشده را تأیید می‌کند (`AP-12`).
- **اجرا** — روش اتصال و SSL لبه و origin در D-26 تعیین شده است. P5.3 فعال‌سازی دو دامنهٔ آزمایشی و آزمون HTTPS را پوشش می‌دهد.

## D-11 — REST + OpenAPI + کلاینت typed ✅

- **تصمیم:** API از نوع REST با قرارداد OpenAPI؛ کلاینت TypeScript از روی آن تولید می‌شود (`packages/api-client`).
- **چرا:** یک منبع حقیقت؛ Storefront و Admin هماهنگ می‌مانند.
- **وسوسه:** «تایپ‌ها را دستی کپی کنیم» ← رد (`AP-22`). «GraphQL/gRPC بزنیم» ← بدون نیاز مشخص رد.

## D-12 — Monorepo: pnpm workspace + Go module مستقل ✅

- **تصمیم:** یک repo شامل `apps/` (storefront، admin، api)، `packages/` (کدهای مشترک TS)، `infrastructure/`.
- **چرا:** تغییرات هماهنگ (مثلاً API + کلاینت + UI) در یک کامیت؛ Go وابستگی به Node.js ندارد.

## D-13 — ذخیره فایل: S3-compatible + Presigned URL ✅

- **تصمیم:** تصاویر در Object Storage سازگار با S3؛ آپلود مستقیم از مرورگر با Presigned URL؛ اعتبارسنجی نوع و حجم. فیلم و فایل صوتی طبق D-32 از همان زیرساخت استفاده می‌کنند.
- **چرا:** سرور اصلی بار فایل را نمی‌کشد (RAM و پهنای باند)؛ جایگزینی ارائه‌دهنده آسان است.
- **ارائه‌دهنده** — S3 پارس‌پک در ایران طبق D-26. Presigned upload و CORS در حساب هدف آزموده می‌شوند.

## D-14 — پول به‌صورت عدد صحیح

- **✅ قاعدهٔ قطعی** — دیتابیس و API مبلغ را به ریالِ صحیح نگه می‌دارند. نوع ذخیره‌سازی `bigint` در PostgreSQL و `int64` در Go است. رابط فارسی مبلغ را به تومان نمایش می‌دهد و رقم ریالی را در نمایش از دست نمی‌دهد. تبدیل به واحد مورد انتظار درگاه داخل adapter پرداخت است. استفاده از float ممنوع است.
- **چرا:** خطای گرد کردن در محاسبات مالی غیرقابل‌قبول است.
- **گرد کردن** — انتهای هر محاسبهٔ درصدی، نتیجه یک بار به نزدیک‌ترین ریال با قاعدهٔ نیم‌به‌بالا گرد می‌شود. نمونه‌های آزمون مرز گرد کردن در `P0.2.2` ثبت می‌شوند.
- **ارتباط:** `AP-06`.

## D-15 — Snapshot در سفارش

- **✅ قاعدهٔ قطعی** — نام، SKU و قیمت زمان خرید در `order_items` ذخیره می‌شوند. تغییر بعدی محصول اقلام سفارش قبلی را تغییر نمی‌دهد.
- **✅ قاعدهٔ قطعی** — مجموع‌های محاسبه‌شدهٔ سفارش همراه با Snapshot اقلام در زمان خرید ذخیره می‌شوند.
- **چرا:** تغییر بعدی محصول نباید سفارش قدیمی را تغییر دهد (فاکتور و حسابداری).
- **ارتباط:** `AP-08`.

## D-16 — کاهش اتمیک موجودی

- **✅ قاعدهٔ قطعی** — کاهش موجودی با UPDATE شرطی داخل تراکنش ساخت سفارش انجام می‌شود. موجودی منفی ممنوع است.
- **✅ قید دیتابیس** — قید `CHECK` روی ستون موجودی نیز از مقدار منفی جلوگیری می‌کند.
- **چرا:** جلوگیری از فروش بیش از موجودی در درخواست‌های هم‌زمان.
- **وسوسه:** «ابتدا بخوانیم و بعد بنویسیم» ← رد (`AP-07`).

## D-17 — پرداخت: interface مشترک + Verify Idempotent

- **✅ قاعدهٔ قطعی** — پرداخت با سرور درگاه تأیید می‌شود. Verify تکراری اثر موفقیت را دوباره اعمال نمی‌کند. تنظیمات حساس درگاه هر فروشگاه رمزنگاری‌شده ذخیره می‌شوند.
- **تسک ثبت‌شده** — `P2.6.1` قرارداد مشترک `PaymentProvider` را تعریف می‌کند و درگاه اولیه در `P2.6.2` آن را پیاده می‌کند.
- **چرا:** درگاه‌ها عوض و اضافه می‌شوند؛ Callback تکراری معمول است و نباید اثر دوباره بگذارد.
- **درگاه اول** — زرین‌پال با پذیرندگی هر فروشگاه و تسویه به همان فروشگاه. واحد مبلغ، حالت تست و تطابق Callback/Verify را در `P2.6` با مستندات و حساب هدف بررسی کن. [مستندات زرین‌پال](https://www.zarinpal.com/docs/)
- **ارتباط:** `AP-09`، `AP-21`.

## D-18 — ارتباط داخلی HTTP؛ بدون message queue ✅

- **تصمیم:** در نسخه‌ی اول ارتباط داخلی با HTTP. جدول `outbox_events` در PostgreSQL نقش صف را دارد.
- **چرا:** یک سرویس کمتر و پیچیدگی کمتر. نیاز فعلی (ابطال کش و کارهای پس‌زمینه) با Outbox پوشش داده می‌شود.
- **وسوسه:** «RabbitMQ/Kafka/NATS بگذاریم.» ← رد (`AP-20`) تا نیاز واقعی و اندازه‌گیری‌شده.

## D-19 — نقش‌های دیتابیس و RLS اجباری ✅

- **تصمیم:** `migrator` مالک جدول‌ها و اجراکننده‌ی Migration؛ `app_user` نقش runtime، بدون superuser و بدون `BYPASSRLS`؛ جدول‌ها `FORCE ROW LEVEL SECURITY` دارند.
- **چرا** — نقش runtime کم‌اختیار است و RLS اجباری، اجرای policy را برای مالک جدول نیز برقرار می‌کند. نقش‌های lookup و Worker طبق D-28 جدا و محدود هستند.
- **ارتباط:** `AP-02`، الگوی ۰۲، تست نگهبان در الگوی ۰۳.

## D-20 — استقرار: Docker Compose + Caddy + کمترین سرویس همیشه‌روشن ✅

- **وسوسه:** Kubernetes / Redis Cluster از روز اول ← رد (D-01، D-05).

## D-26 — زیرساخت ایران، آروان، پارس‌پک و TLS ✅

- **انتخاب صاحب پروژه** — CDN آروان‌کلاد و Object Storage سازگار با S3 پارس‌پک در ایران. DNS پلتفرم نیز روی آروان است. نام APIها و تنظیمات محیط از مستندات فعلی و حساب هدف گرفته می‌شوند. [مستندات CDN آروان](https://docs.arvancloud.ir/fa/cdn) · [مستندات S3 پارس‌پک](https://docs.parspack.com/cloud-storage/)
- **میزبان پایلوت** — VPS لینوکسی پارس‌پک در ایران با هدف اولیهٔ ۴ vCPU، ۸ گیگابایت RAM و حداقل ۸۰ گیگابایت SSD. PostgreSQL و برنامه با Docker Compose روی همین میزبان هستند. پشتیبان رمزنگاری‌شده خارج از دیسک VPS نگه‌داری می‌شود. تست بار و بازیابی ظرفیت نهایی را مشخص می‌کنند.
- **DNS و TLS** — پس از تأیید مالکیت، آروان لبهٔ دامنه و گواهی کاربر را مدیریت می‌کند. برای دامنهٔ ریشه، NS Delegation مسیر اصلی است. برای زیردامنه نزد DNS بیرونی، از CNAME Setup در پلن رشد یا بالاتر استفاده می‌شود. پلن هدفِ الگوی کامل دامنهٔ اختصاصی، رشد است. Caddy در origin با HTTPS معتبر پاسخ می‌دهد و صدور گواهی origin به دامنه‌های تأییدشده محدود است. در مسیر origin، تطابق Host فروشگاه و اعتبار TLS در محیط هدف آزموده می‌شوند. [راه‌اندازی دامنه و HTTPS آروان](https://docs.arvancloud.ir/fa/cdn) · [پلن لازم برای CNAME Setup](https://docs.arvancloud.ir/fa/cdn/domain/cname-setup)
- **کش و ابطال** — کش مشترک HTML فقط برای خانه، دسته و محصول عمومی canonical بدون query string فعال است. پاسخ شخصی، جستجو، فیلتر و pagination دارای query از کش مشترک عبور نمی‌کنند. Worker فقط URLهای متعلق به Host تأییدشدهٔ Tenant و متأثر از رویداد را با API CDN آروان purge می‌کند. روش Tag در مدل فعلی API به‌عنوان منسوخ علامت‌گذاری شده است. با تغییر slug، دسته یا وضعیت انتشار، URL قبلی و جدید و فهرست‌های متأثر در محدودهٔ همان فروشگاه بررسی می‌شوند. کش HTML پس از آماده‌شدن Outbox و Worker فعال می‌شود. فونت‌ها و فایل‌های رابط در زمان اجرا از مسیر داخلی ارائه می‌شوند. [API کش آروان](https://github.com/arvancloud/cdn-go/blob/main/docs/CachingApi.md) · [مدل Purge آروان](https://github.com/arvancloud/cdn-go/blob/main/docs/CachingPurge.md)
- **تأیید محیط** — پیش از عرضه، اتصال دو دامنه، صدور و تمدید گواهی، جداسازی Host در کش، URL purge، و دسترسی کاربران ایرانی به CDN و پرداخت را روی محیط واقعی بررسی کن. برای پارس‌پک، upload امضاشده، CORS، نوع و حجم فایل و دسترسی به تصاویر منتشرشده باید روی باکت هدف آزموده شوند.
- **تاریخچه** — انتخاب قبلی Cloudflare و اتکای به Cache Tag در D-06، D-07، D-10 و D-20 با این تصمیم جایگزین شدند. Outbox تراکنشی و مرز Caddy پابرجا هستند.

## D-27 — نشست، هش رمز و نقش‌های پنل ✅

- **نشست** — شناسهٔ تصادفی نشست در کوکی `HttpOnly`، `Secure` و محدود به Host نگه‌داری می‌شود و وضعیت نشست در PostgreSQL است. نشست مدیر و مشتری مستقل‌اند. انقضا سمت سرور و ابطال هنگام logout اعمال می‌شوند. تمدید کنترل‌شده و چرخش شناسه به‌همراه محافظت درخواست‌های تغییردهنده در طراحی Auth مشخص می‌شوند.
- **رمز و هویت** — هش Argon2id. ایمیل مدیر در محدودهٔ هویت مدیر و ایمیل مشتری در محدودهٔ Tenant خودش یکتا است. [راهنمای ذخیرهٔ رمز](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) · [راهنمای نشست](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)
- **نقش‌های اولیه** — `owner` عملیات مدیریتی فروشگاه و مدیریت اعضا، دامنه و تنظیمات پرداخت را انجام می‌دهد. `admin` کاتالوگ، تصاویر، موجودی و عملیات سفارش را مدیریت می‌کند و مشتریان را در محدودهٔ همان فروشگاه می‌بیند. `staff` ابتدا فقط کاتالوگ را می‌خواند. دسترسی هر عملیات به‌صراحت در Backend ثبت و آزموده می‌شود.

## D-28 — lookup اولیه و دسترسی Worker با RLS ✅

- **lookup اولیه** — عملیات خواندن محدود دیتابیس از طریق sqlc و نقش‌های کم‌اختیار انجام می‌شوند و policyهای RLS فعال‌اند. مسیر دامنه فقط نگاشت Host تأییدشده و حداقل فیلد لازم را می‌دهد. مسیر عضویت فقط عضویت‌های هویت احرازشده را برمی‌گرداند. lookup اولیه مجوز تغییر یا دسترسی عمومی به این جدول‌ها نمی‌دهد. پس از تعیین Tenant، مسیر عادی از `WithTenantTx` استفاده می‌کند. [مستندات RLS در PostgreSQL](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)
- **Worker** — نقش جداگانهٔ بدون `BYPASSRLS` با policy صریح برای رویدادهای Outbox در چند Tenant. مجوزها به خواندن و ثبت وضعیت پردازش در `outbox_events` محدودند. دادهٔ لازم برای purge از رویداد معتبر تأمین می‌شود. آزمون‌های نگهبان دامنهٔ نقش lookup و Worker و ایزولاسیون API را بررسی می‌کنند.
- **ترتیب** — قرارداد و policy lookup در P0.2 و پیش از `P1.2.3` و `P1.2.4` طراحی می‌شوند. policy Worker در `P5.1` پیاده می‌شود.

## D-29 — سبد، Checkout و انقضای سفارش ✅

- **سبد** — سبد مهمان و مشتری در PostgreSQL و در محدودهٔ Tenant نگه‌داری می‌شود. پس از ورود، سبد مهمان همان فروشگاه به سبد مشتری منتقل یا ادغام می‌شود. خرید نهایی به حساب مشتری همان فروشگاه نیاز دارد.
- **شرط خرید آنلاین** — حالت فروشگاه و وضعیت قیمت فعلی کالاها طبق D-31 بررسی می‌شوند.
- **انقضا** — سفارش پرداخت‌نشده مهلت پرداخت قابل تنظیم دارد. پیش‌فرض پایلوت ۳۰ دقیقه است و با عمر تلاش درگاه هماهنگ می‌شود. پس از پایان مهلت، لغو زمانی انجام می‌شود که تلاش پرداختی وجود نداشته باشد یا نتیجهٔ نهایی آن ناموفق یا منقضی باشد. لغو و برگشت موجودی تراکنشی و یک‌باره‌اند. هم‌زمانی Verify و انقضا باید تست شود.
- **پرداخت‌شده** — لغو خودکار و بازپرداخت خودکار سفارش پرداخت‌شده خارج از MVP هستند. ثبت پرداخت موفق از مسیر Verify انجام می‌شود.

## D-30 — اختیار اجرای محلی و گزارش ایجنت ✅

- **اجرا** — پس از درخواست شروع پیاده‌سازی، ایجنت تسک‌های آماده را به‌ترتیب و در گروه‌های کوچک محلی اجرا می‌کند. پس از بررسی معیار پذیرش و ثبت نتیجه، چک‌باکس تسک تکمیل‌شده را تیک می‌زند. جزئیات کم‌ریسک مثل قالب خطا، سقف آپلود و رفتار حذف دسته در قرارداد همان تسک با آزمون ثبت می‌شوند.
- **مرز اختیار** — تغییر تصمیم‌های ثبت‌شده، دامنهٔ محصول، قواعد مالی یا اعطای دسترسی به تأیید نیاز دارد. خرید سرویس، push، merge، تغییر DNS و انتشار واقعی هم تأیید جداگانه می‌خواهند.
- **CI** — تست و اسکریپت‌های CI در مخزن و قابل اجرای محلی هستند. runner استقرار بر بستر مورد تأیید در ایران قرار می‌گیرد.

## D-31 — حالت خرید فروشگاه و تماس برای قیمت ✅

مالک هر فروشگاه حالت خرید را در تنظیمات همان فروشگاه انتخاب می‌کند. پیش‌فرض «خرید آنلاین» است.

| حالت | رفتار سبد و اقدام مشتری |
| --- | --- |
| خرید آنلاین | کالای قیمت‌دار طبق D-29 وارد سبد و checkout می‌شود. کالای «تماس برای قیمت» شمارهٔ عمومی فروشگاه را نشان می‌دهد و به سبد خرید آنلاین اضافه نمی‌شود. |
| فقط تماس | کاتالوگ در دسترس است و اقدام خرید، تماس با فروشگاه است. افزودن به سبد، ثبت سفارش آنلاین و شروع پرداخت در دسترس نیستند. |
| سبد و تماس | مشتری می‌تواند کالاهای قیمت‌دار و «تماس برای قیمت» را در سبد جمع کند. در مرحلهٔ نهایی، شمارهٔ فروشگاه برای هماهنگی خرید نمایش داده می‌شود. سبد به سفارش آنلاین یا پرداخت تبدیل نمی‌شود. |

- **قیمت نامشخص** — «تماس برای قیمت» برای کل محصول قابل انتخاب است. محصول در این حالت می‌تواند بدون مبلغ منتشر شود و قیمت هیچ‌یک از تنوع‌هایش در خروجی عمومی نمایش داده نمی‌شود. پولِ ثبت‌شده همچنان ریال صحیح است. مبلغ ناموجود، از مقدار عددی صفر متمایز است و در جمع نهایی یا پیشنهاد قیمت ساخت‌یافته به‌عنوان مبلغ استفاده نمی‌شود.
- **شمارهٔ عمومی** — حالت تماسی و انتشار کالای «تماس برای قیمت» به شمارهٔ عمومی معتبر همان فروشگاه نیاز دارند. شماره در تنظیمات فروشگاه ثبت می‌شود و تا وقتی یک حالت یا کالای منتشرشده به آن نیاز دارد، باید معتبر بماند.
- **کنترل Backend** — قبل از ثبت سفارش آنلاین و شروع تلاش پرداخت جدید، Backend حالت جاری Tenant را از منبع اصلی بررسی می‌کند. مجاز بودن کالا و قیمت جاری در تراکنش ساخت سفارش بررسی می‌شوند. تغییر حالت و پذیرش عملیات جدید باید ترتیب سازگار داشته باشند. در حالت تماسی سفارش آنلاین، کسر موجودی و تلاش پرداخت جدید ایجاد نمی‌شود.
- **تغییر حالت و تراکنش‌های قبلی** — سبدهای قبلی حفظ و در استفادهٔ بعدی با حالت و قیمت جاری بازبینی می‌شوند. Snapshot سفارش‌های ثبت‌شده پابرجاست. Verify پرداختی که پیش از تغییر حالت شروع شده طبق D-17 ادامه دارد.
- **نمایش و کش** — همهٔ قالب‌ها از همین حالت‌ها پیروی می‌کنند. تغییر حالت خرید، شمارهٔ تماس یا وضعیت قیمت که بر HTML عمومی اثر می‌گذارد طبق D-07 و D-26 در همان تراکنش رویداد Outbox ثبت می‌کند. پاسخ سبد و مرحلهٔ نهایی `no-store` است.

## D-32 — بلاگ و رسانهٔ محصول و مطلب ✅

- **بلاگ فروشگاه** — فروشندهٔ دارای مجوز از پنل می‌تواند پیش‌نویس مطلب بسازد، آن را ویرایش کند، منتشر کند و از انتشار خارج کند. Storefront فهرست و صفحهٔ مطالب منتشرشدهٔ همان فروشگاه را نمایش می‌دهد. قابلیت بلاگ به حالت خرید فروشگاه وابسته نیست.
- **فیلم و ویس** — فروشندهٔ مجاز فایل ویدئو یا صوت را از پنل مستقیم به S3 پارس‌پک آپلود می‌کند و فایل تأییدشده را به مطلب بلاگ یا محصول همان Tenant وصل می‌کند. بازدیدکننده رسانهٔ منتشرشده را در همان صفحه پخش می‌کند.
- **محتوا و دسترسی** — بدنهٔ مطلب با بلوک‌های تأییدشدهٔ متن و رسانه رندر می‌شود. مطلب و رسانهٔ منتشرنشده دسترسی عمومی ندارند. فرم پنل و عملیات انتشار با مجوز Backend و RLS همان Tenant کنترل می‌شوند. اعتبار نوع، حجم و محتوای فایل قبل از انتشار بررسی می‌شود.
- **نمایش و کش** — HTML بلاگ در نسخهٔ اول از کش مشترک عبور می‌کند و پاسخ پیش‌نویس خصوصی و `no-store` است. تغییر رسانهٔ محصول که HTML عمومی آن را عوض می‌کند طبق D-07 با Outbox ابطال می‌شود. نمایش عمومی فایل با وضعیت انتشار و پیوندهای فعلی همان فروشگاه هماهنگ می‌ماند.
- **ارتباط** — مدل داده و قرارداد در `P0.2.10` و `P0.3.8`، آپلود و بلاگ در `P2.2.6` و `P2.8`، نمایش و پخش در `P3.3.10` و `P3.3.11`، و ویرایش و انتشار در `P4.2.15`.

2. در پیام‌ات بنویس: کدام تصمیم (`D-XX`)، مشکل مشخصی که با آن دیدی (ترجیحاً با عدد یا خطای واقعی، نه «تمیزتر می‌شود»)، حداقل یک گزینه‌ی جایگزین، و هزینه‌ی تغییر.
3. بعد از تأیید من، تصمیم قبلی را حذف نکن؛ وضعیتش را `⛔ جایگزین شد با D-YY` بگذار و تصمیم جدید را با شناسه‌ی تازه اضافه کن (تاریخچه حفظ شود).
4. فایل‌های وابسته را هم هماهنگ کن: `ANTI_PATTERNS.md`، `docs/patterns/`، `AGENTS.md`، `TASKS.md`.

## چطور تصمیم جدید ثبت کنیم

قالب هر مورد: `D-XX — عنوان` · **وضعیت** · **تصمیم** · **چرا** · **وسوسه (و چرا رد شد)** · **بازبینی وقتی** · **ارتباط**.
تصمیم تازه تا تأیید من 🟡 است.
